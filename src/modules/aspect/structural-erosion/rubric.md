# Structural erosion

`structural-erosion` · default ON

**Question:** Does the change create or worsen an overloaded unit by coupling responsibilities, dependencies or state?

**Applies when:** The change adds responsibilities, branches or state to an existing function, class or module. Otherwise return not-applicable.

**Evidence:** Base the review on changed hunks and the affected unit, or the assessed unit in a repository audit. Trace shared flags and error state from their writers to every phase they gate; check whether failure in one responsibility disables another. Name the responsibilities coupled and the resulting cost, such as tests needing another mocked layer. Show the boundary a correction restores without merely distributing the same complexity across files. Length and complexity metrics are only clues.

**Boundaries:** In a change review, a finding must arise from the change, not the file's general condition. In a repository audit, assess existing coupling against current product boundaries. Lifecycle orchestration can legitimately coordinate several phases of one responsibility. Do not propose broad refactoring unrelated to the assessed scope.

**Not here (another reviewer):**
- More mechanism than one existing responsibility needs, without added responsibilities, dependencies or coupling: unnecessary-complexity.
- Copying existing code instead of reusing it: missed-reuse.
- A shared mechanism combining cases with divergent rules: wrong-abstraction.
- Departure from an established repository pattern without increased coupling: convention-drift.

Teaching excerpts; context states omitted setup. These have not been executed as programs or model evaluations.

## structural-erosion-B1 · REPORT

**Context:** A large function already mixes billing, transport and formatting. A new user type adds interdependent exceptions in each area.

```typescript
if (user.kind === "partner") skipFee = true;
// unrelated network and formatting code
if (user.kind === "partner" && !legacy) response.mode = "special";
// later in the same procedure
if (skipFee && response.mode !== "special") retryBilling();
```

**Why:** The change scatters one policy across an existing complex path and couples distant states. Cite those dependencies, not just line count.

## structural-erosion-B2 · REPORT

**Context:** OrderRepository previously only stored and retrieved orders. The diff adds confirmation emails with attached PDF invoices. Repository tests now need mailer and renderer mocks.

```typescript
async saveAndNotify(order: Order) {
  await this.save(order);
  await mailer.send(order.email, renderInvoicePdf(order));
}
```

**Why:** The data layer acquires transport and template dependencies, so email changes affect the repository and its tests gain unrelated mocks. Evidence is the unit's new dependencies and testing cost, not line count.

## structural-erosion-B3 · REPORT

**Context:** A persistence function now absorbs transport retry policy and legacy billing overrides, marked // new. Partial retries must never be persisted, including forced legacy operations, but both policies mutate the same save decision.

```typescript
let shouldSave = true;                                // new
if (retry) { if (partial) shouldSave = false; }       // new
if (legacy) { if (forced) shouldSave = true; }        // new
if (shouldSave) await save(result);
```

**Why:** For retry && partial && legacy && forced, billing's override defeats the transport policy. These responsibilities are coupled through mutable persistence state. Resolve their policy before the persistence boundary rather than scattering overrides through it; branch count alone would not establish this defect.

## structural-erosion-G1 · PRESERVE

**Context:** A new permitted state is added to one exhaustive dispatch; each branch has a coherent responsibility.

```typescript
switch (job.state) {
  case "ready": return start(job);
  case "running": return inspect(job);
  case "paused": return continueJob(job); // new state
  case "done": return report(job);
  default: return assertNever(job.state);
}
```

**Why:** Additional cases follow the domain model. Branching remains local and understandable.

## structural-erosion-G2 · PRESERVE

# Generated by scripts/gen_errors.py. DO NOT EDIT.
ERROR_NAMES = {

**Why:** Line count alone does not measure structural erosion. Generated data may also be excluded from review.

## structural-erosion-G3 · PRESERVE

**Context:** The guard covers one new valid case and terminates it before the existing path.

```typescript
if (items.length === 0) return emptyReport();
return buildReport(items);
```

**Why:** The extra condition simplifies subsequent assumptions without scattering the special case through the function.
